# エラーログ仕様

このドキュメントは、いいね・ブックマーク・RT・投稿・Sheets同期で失敗したときに残るエラーログの仕様をまとめたものです。
通常の進行ログではなく、失敗調査に必要なログだけを対象にします。

## エラーログの種類

| 種類 | 保存先 | 主な用途 |
| --- | --- | --- |
| コンソールエラー | 標準出力 | 実行中の即時確認 |
| `last_error_summary` | メモリ上の `TwitterAPI` / `Tweeter` インスタンス | 直近失敗の短い分類 |
| `failed_actions.jsonl` | ルート直下 | 機械処理しやすい失敗履歴 |
| `failed_actions.txt` | ルート直下 | 人間が読む失敗履歴 |
| API詳細デバッグブロック | 標準出力 | HTTPレスポンス、payload、ヘッダー確認 |
| `tid_node/server.log` | `tid_node/server.log` | TIDサーバー起動・生成失敗の調査 |
| Sheets結果列 | Google Sheets | 投稿系の状態反映、失敗概要保存 |

## failed_actions.jsonl

`test.py` の `append_failed_action_log()` が、アクション失敗時に追記する。
1行1JSON形式。

主な記録対象:

- impression失敗
- like失敗
- bookmark失敗
- retweet失敗
- natural_action内のroute失敗
- 診断後も曖昧な失敗

主なフィールド:

| Field | 型 | 説明 |
| --- | --- | --- |
| `account_id` | number/null | DB上のアカウントID |
| `screen_name` | string/null | 実行アカウント名 |
| `tweet_id` | string | 対象ツイートID |
| `execution_type` | string | `impression`, `like`, `bookmark`, `retweet` など |
| `reason` | string | 失敗理由。基本は `last_error_summary` |
| `result_snapshot` | object | 失敗時の結果辞書の抜粋 |

`result_snapshot` に入り得る主なキー:

| Key | 説明 |
| --- | --- |
| `impression` | impression成否 |
| `like` | いいね成否 |
| `bookmark` | ブックマーク成否 |
| `retweet` | RT成否 |
| `impression_reason` | impression失敗理由 |
| `like_reason` | いいね失敗理由 |
| `bookmark_reason` | ブックマーク失敗理由 |
| `retweet_reason` | RT失敗理由 |
| `diagnosis` | 追加診断の結果 |
| `diagnostic_probes` | read-only probe結果 |

例:

```json
{"account_id":1,"screen_name":"TamaraRodrigu47","tweet_id":"2063399770534891857","execution_type":"retweet","reason":"TOKEN_EXPIRED_OR_INVALID | HTTP 401 code=32 message=Could not authenticate you","result_snapshot":{"retweet":false}}
```

## failed_actions.txt

`failed_actions.jsonl` と同じ失敗を、人間向けに区切り線付きで追記する。

形式:

```text
======================================================================
account_id: 1
screen_name: TamaraRodrigu47
tweet_id: 2063399770534891857
execution_type: retweet
reason: TOKEN_EXPIRED_OR_INVALID | HTTP 401 code=32 message=Could not authenticate you
```

用途:

- ざっと目視で失敗アカウントを確認する
- JSONを開かずに `reason` を読む
- 同じ失敗が連続しているか確認する

## last_error_summary

`last_error_summary` は直近の失敗を短く分類する文字列。
成功時は原則 `None` に戻る。

主なセット箇所:

| 出力元 | 主な対象 |
| --- | --- |
| `TwitterAPI._classify_api_failure()` | X API HTTP失敗 |
| `TwitterAPI._execute_via_native_curl()` | like/bookmark/RT/CreateTweet系送信失敗 |
| `TwitterAPI.fetch_home_timeline()` | HomeTimeline失敗 |
| `TwitterAPI.view_tweet()` | TweetDetail失敗 |
| `TwitterAPI.fetch_user_profile()` | UserByScreenName失敗 |
| `TwitterAPI.send_client_event_log()` | impression/client_event失敗 |
| `tweet.py` / `Tweeter` | 投稿失敗 |

代表的な分類:

| Prefix | 意味 | よくある原因 | 対応 |
| --- | --- | --- | --- |
| `TOKEN_EXPIRED_OR_INVALID` | 認証失敗 | Cookie古い、auth_token/ct0不一致、間違ったシートをpull | 正しいシートからDB更新、再ログインCookie確認 |
| `ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED` | ロック/認証要求 | challenge、本人確認 | ブラウザで状態確認 |
| `ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED` | 凍結/停止/無効化 | アカウント状態異常 | 対象から除外、状態確認 |
| `RATE_LIMITED` | レート制限 | 429、code 88 | 待機、実行数削減 |
| `SPAM_OR_AUTOMATION_DETECTED` | 自動化/スパム判定 | code 226 | 操作間隔を広げる、対象アカウント確認 |
| `POST_LIMIT_OR_COOKIE_DEGRADED` | 投稿制限/Cookie劣化 | code 344 | Cookie再取得、投稿頻度確認 |
| `FORBIDDEN_OR_PERMISSION_DENIED` | 権限拒否 | 403 | 対象ツイート/アカウント状態確認 |
| `ENDPOINT_OR_OPERATION_NOT_FOUND` | endpoint/queryId不一致 | 404、X側仕様変更 | operation queryId確認 |
| `UNKNOWN_API_ERROR` | 未分類API失敗 | レスポンス形式変更など | Response Preview確認 |
| `通信例外エラー` | 通信例外 | proxy、TLS、timeout | proxy/ネットワーク確認 |
| `TID取得失敗` | transaction id生成失敗 | Node.js TIDサーバー不調 | `tid_node/server.log`確認 |

## API詳細デバッグブロック

`_execute_via_native_curl()` が送信失敗と判定した場合、標準出力に詳細ブロックを出す。

形式:

```text
======================================================================
[ERROR] API Request Failed - Debug Information
======================================================================
Error Type: Authentication Failed (401 Unauthorized)
Error Message: Could not authenticate you
Keyword Expected: ['"retweet":"Done"', '"create_retweet":"Done"', '"retweeted":true', '"retweet_results"']
Keyword Found: False
Has Errors Field: True

[DEBUG] Curl Command (auth tokens masked):
...

[DEBUG] Response Preview (first 1500 chars):
{"errors":[{"message":"Could not authenticate you","code":32}]}
======================================================================
```

項目の意味:

| 項目 | 説明 |
| --- | --- |
| `Error Type` | HTTP状態や成功判定失敗の大分類 |
| `Error Message` | X APIの `errors[0].message`。なければ `No error message` |
| `Keyword Expected` | 成功判定に使った文字列 |
| `Keyword Found` | 成功判定文字列がレスポンス内にあったか |
| `Has Errors Field` | レスポンスに `errors` があったか |
| `Curl Command` | 再現/確認用のcurl風コマンド。認証情報の扱い注意 |
| `Response Preview` | レスポンス本文先頭1500文字 |

重要:

- HTTP 200でも `Keyword Found=False` なら失敗扱いになる。
- X側レスポンス形式が変わった場合は `Response Preview` を見て成功判定を更新する。
- RT成功は `retweet_results.result.rest_id` が返ることがあるため、`"retweet_results"` を成功判定に含める。

## read-only診断ログ

`test.py` の `diagnose_failures()` は、曖昧な失敗時に読み取り専用probeを実行する。

実行するprobe:

| Probe | 内容 |
| --- | --- |
| `tweet_detail_ok` | 対象ツイート詳細が読めるか |
| `self_profile_ok` | 自アカウントプロフィールが読めるか |
| `home_timeline_ok` | HomeTimelineが読めるか |

診断結果例:

| diagnosis | 意味 |
| --- | --- |
| `DIAG_READ_OK_ACTION_ONLY_FAILURE` | 読み取りはOK。アクションendpoint/TID/権限などが怪しい |
| `DIAG_READ_PROBES_FAILED` | 読み取りも失敗。Cookie/proxy/account状態が怪しい |
| `DIAG_MIXED_READ_PROBES` | probeごとに結果が混在 |

## よくあるエラーと確認順

### 401 / code 32

表示例:

```text
TOKEN_EXPIRED_OR_INVALID | HTTP 401 code=32 message=Could not authenticate you
```

確認順:

1. 正しいシートをpullしたか
   - いいね/ブクマ/RT系は `非公式API情報いいね垢`
2. `--db like_accounts.db` を付けたか
3. DB内の対象アカウントCookieに `auth_token`, `ct0`, `twid` があるか
4. `auth_token`列とcookies内`auth_token`がズレていないか
5. 保存Fingerprintが必要なアカウントではないか
6. 読み取りAPIも401ならCookie自体が無効

正しいpull例:

```bash
python sheets_sync.py pull --sheet "非公式API情報いいね垢" --db like_accounts.db
```

### HTTP 200だが失敗扱い

表示例:

```text
Error Type: Success Keyword Not Found (200 OK but invalid response)
Keyword Found: False
Response Preview: {"data":{"create_retweet":{"retweet_results":...}}}
```

意味:

- API操作自体は成功している可能性がある。
- 成功判定キーワードがレスポンス形式に合っていない。

対応:

- `Response Preview` に成功を示すフィールドがあるか見る。
- 必要なら `success_keyword` に新しい判定文字列を追加する。

### TID取得失敗

表示例:

```text
ENGAGEMENT TID取得失敗: Node.js TID server returned no transaction id
```

確認順:

1. Node.jsが起動できるか
2. `tid_node/server.js` が存在するか
3. `http://127.0.0.1:3000/status` が応答するか
4. `tid_node/server.log` を見る

### IMPRESSION失敗

表示例:

```text
IMPRESSION failed: all endpoints rejected the request
```

確認順:

1. `jot/client_event.json` のTID生成が成功しているか
2. Cookieが有効か
3. referer/pageが自然な経路になっているか
4. `Response Preview` のHTTP status/codeを見る

### GraphQL operation queryId解決失敗

表示例:

```text
[ROUTE] CreateRetweet query id not found; set X_QUERY_ID_CREATE_RETWEET to override
```

確認順:

1. bootstrap_pathが適切か
   - `CreateRetweet` は `/home` 側JSから解決する
2. X側JS構造が変わっていないか
3. 環境変数 `X_QUERY_ID_CREATE_RETWEET` で一時上書きできるか

## Sheets / DB同期エラー

`sheets_sync.py` の失敗・警告:

| ログ | 意味 | 対応 |
| --- | --- | --- |
| `[ERROR] シート名 ... が見つかりません` | タブ名違い | `--sheet` を確認 |
| `[WARN] データが空です` | シートが空 | 対象URL/タブ確認 |
| `[SKIP] クッキー空欄` | Cookieが空 | Sheetのcookies列確認 |
| `[WARN] Cookieに 'ct0' が見つかりません` | CSRF不足 | Cookie再取得 |
| `[ERROR] エラーが発生しました` | gspread/API/認証など | service_account, 権限, ネットワーク確認 |

注意:

- `sheets_sync.py pull` のデフォルトDBは `accounts.db`。
- `test.py` は `like_accounts.db` を使う。
- いいね/ブクマ/RTのテスト前は、必ず以下を使う。

```bash
python sheets_sync.py pull --sheet "非公式API情報いいね垢" --db like_accounts.db
```

## 投稿系エラーログ

`tweet_post.py` / `tweet.py` の投稿失敗では、以下が主に出る。

| Prefix | 意味 |
| --- | --- |
| `[TWEET_DIAG]` | 投稿前診断情報 |
| `[FAILED]` | 投稿失敗 |
| `[DIAG] account_id=... execution_type=tweet reason=...` | 投稿失敗理由の保存用概要 |
| `[SHEET] ... result synced` | Sheetへの結果反映成功 |
| `[WARN] ... sheet result sync failed` | Sheet結果反映失敗 |

投稿失敗時は `last_error_summary` にCreateTweet系の失敗分類と診断情報が連結されることがある。

## アカウント状態エラー詳細

このセクションは、他開発者が `last_error_summary` の分類結果を見て、どの状態として扱うべきか判断できるようにするための実装メモです。
分類の入口は主に `twitter_api.py` の `_classify_api_failure(status_code, response_body, error_message)` です。

### 分類優先度

複数条件に該当し得る場合は、現在の実装では概ね以下の順に分類される。

1. `TOKEN_EXPIRED_OR_INVALID`
2. `ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED`
3. `ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED`
4. `RATE_LIMITED`
5. `SPAM_OR_AUTOMATION_DETECTED`
6. `POST_LIMIT_OR_COOKIE_DEGRADED`
7. `FORBIDDEN_OR_PERMISSION_DENIED`
8. `ENDPOINT_OR_OPERATION_NOT_FOUND`
9. `API_ERROR` / `UNKNOWN_API_ERROR`

開発者が新しい条件を足す場合は、より具体的で復旧不能に近い状態を上位に置く。
ただし `401/code=32` はCookie不整合で頻出するため、トークン切れとして最優先に扱う。

### トークン切れ / Cookie無効

分類名:

```text
TOKEN_EXPIRED_OR_INVALID
```

主な検出条件:

| 条件 | 例 |
| --- | --- |
| HTTP status | `401` |
| X error code | `32` |
| message/body | `Could not authenticate you`, `not authorized`, `invalid or expired token` |
| ローカル状態 | Cookieに `auth_token` がない、`ct0` がない、auth_token列とcookies内auth_tokenが不一致 |

代表ログ:

```text
TOKEN_EXPIRED_OR_INVALID | HTTP 401 code=32 message=Could not authenticate you
```

API詳細ブロック例:

```text
Error Type: Authentication Failed (401 Unauthorized)
Error Message: Could not authenticate you
Response Preview:
{"errors":[{"message":"Could not authenticate you","code":32}]}
```

意味:

- X APIがログイン済みセッションとして認めていない。
- RT/いいね/ブクマだけでなく、`TweetDetail`, `HomeTimeline`, `UserByScreenName` など読み取りAPIも401になることが多い。
- Cookieが存在していても、有効とは限らない。

開発者向け確認ポイント:

1. pull元シートが正しいか。
   - いいね/ブクマ/RT系は `非公式API情報いいね垢`。
2. pull先DBが正しいか。
   - `test.py` は `like_accounts.db` を読む。
3. `auth_token`列と `cookies` 列内の `auth_token` がズレていないか。
   - `sheets_sync.py` は cookiesを読んだあと、`auth_token`列があれば `cookies['auth_token']` に上書きする。
4. Cookieに `ct0` があるか。
5. 実行時User-Agent / impersonate がCookie取得時とズレていないか。
   - 必要なら `test.py` の `RUNTIME_UA_OVERRIDES` に対象アカウントを追加する。
6. 同アカウントでread-only probeを実行し、読み取りも401か確認する。

推奨処理:

| 場面 | 推奨 |
| --- | --- |
| 単発テスト | 正しいシートからpullし直す。まだ401なら再ログインCookieを取得する |
| バッチ処理 | そのアカウントの以降のアクションを止める |
| Sheets反映 | statusは `トークン切れ` 相当 |
| 自動再試行 | 原則しない。Cookie更新後のみ再試行 |

実装上の注意:

- `auth_token`, `ct0`, `cf_clearance` が存在しても401なら無効Cookieとして扱う。
- proxy障害でも401風に見えるケースは少ないが、全read probeが通信例外ではなく明確に401ならCookie側を優先する。
- `TOKEN_EXPIRED_OR_INVALID` は「ログイン切れ」だけでなく「CookieとUA/fingerprint不一致」も含む。

### ロック / Challenge要求

分類名:

```text
ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED
```

主な検出条件:

| 条件 | 例 |
| --- | --- |
| X error code | `326` |
| message/body | `locked`, `account is temporarily locked`, `challenge`, `verify your account` |
| 画面状態 | ブラウザでログインすると本人確認、電話番号確認、メール確認、captcha等が出る |

代表ログ:

```text
ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED | HTTP 403 code=326 message=To protect our users from spam and other malicious activity, this account is temporarily locked.
```

想定されるResponse Preview例:

```json
{"errors":[{"message":"To protect our users from spam and other malicious activity, this account is temporarily locked.","code":326}]}
```

意味:

- Cookieが完全に期限切れというより、アカウント側に追加確認が必要な状態。
- APIからの自動操作で復旧できない可能性が高い。
- いいね/ブクマ/RT/投稿は止めるべき状態。

開発者向け確認ポイント:

1. `Response Preview` に `code:326` があるか。
2. body/messageに `locked`, `challenge`, `verify` があるか。
3. ブラウザで対象アカウントを開き、確認画面が出るか。
4. 同じproxy/UAでログイン確認する。
5. Cookie更新だけで直るか、本人確認完了が必要かを分ける。

推奨処理:

| 場面 | 推奨 |
| --- | --- |
| 単発テスト | 即停止し、ブラウザで状態確認 |
| バッチ処理 | 対象アカウントをスキップし、以降の操作を止める |
| Sheets反映 | statusは `ロック/認証要求` 相当 |
| 自動再試行 | しない。人手でchallenge解除後のみ再試行 |

実装上の注意:

- `403` だけでロックとは判断しない。`code=326` または challenge系文言を確認する。
- ロック状態で操作を繰り返すと悪化する可能性があるため、同一アカウント内の後続アクションは止める。
- `ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED` は復旧不能ではないが、人手対応が必要な停止状態として扱う。

### 凍結 / 停止 / 無効化

分類名:

```text
ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED
```

主な検出条件:

| 条件 | 例 |
| --- | --- |
| X error code | `64` |
| message/body | `suspended`, `deactivated`, `offboarded` |
| 画面状態 | ブラウザで凍結、停止、存在しない/無効化扱い |

代表ログ:

```text
ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED | HTTP 403 code=64 message=Your account is suspended and is not permitted to access this feature.
```

想定されるResponse Preview例:

```json
{"errors":[{"message":"Your account is suspended and is not permitted to access this feature.","code":64}]}
```

意味:

- アカウント自体が操作不可状態。
- Cookie更新や再試行で直る種類ではないことが多い。
- バッチ対象から外すべき状態。

開発者向け確認ポイント:

1. `Response Preview` に `code:64` があるか。
2. body/messageに `suspended`, `deactivated`, `offboarded` があるか。
3. ブラウザで対象アカウントの状態を確認する。
4. Sheet/DBのstatusがactiveのままなら更新対象。

推奨処理:

| 場面 | 推奨 |
| --- | --- |
| 単発テスト | 即停止 |
| バッチ処理 | 対象アカウントを除外 |
| Sheets反映 | statusは `凍結` / `停止` / `無効化` 相当 |
| 自動再試行 | しない |

実装上の注意:

- `ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED` は原則として復旧不能寄りの状態として扱う。
- 以降の同一アカウント操作は失敗ログを増やすだけなので止める。
- `status` を更新する仕組みを追加する場合は、この分類を最優先で非active化候補にする。

### 3分類の比較

| 分類 | 典型HTTP/code | Cookie更新で直る可能性 | 人手対応 | 自動再試行 | 推奨status |
| --- | --- | --- | --- | --- | --- |
| `TOKEN_EXPIRED_OR_INVALID` | `401`, `code=32` | 高い | Cookie再取得が必要 | Cookie更新後のみ | `トークン切れ` |
| `ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED` | `403`, `code=326` | 低い | challenge解除が必要 | しない | `ロック/認証要求` |
| `ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED` | `403`, `code=64` | ほぼなし | 状態確認のみ | しない | `凍結` / `停止` |

### 実装者向けフロー

アクション失敗時は以下の順で判定する。

```text
response.status_code == 401 or code == 32
  -> TOKEN_EXPIRED_OR_INVALID

code == 326 or body contains locked/challenge/verify
  -> ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED

code == 64 or body contains suspended/deactivated/offboarded
  -> ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED

status_code == 429 or code == 88
  -> RATE_LIMITED

その他
  -> 403/404/API_ERROR/UNKNOWN_API_ERROR
```

この順序により、ログから対応方針を機械的に決められる。
バッチ処理で実装する場合は、少なくとも上記3分類は「同一アカウントの後続アクション停止」の対象にする。
ただし `TOKEN_EXPIRED_OR_INVALID` は、正しいSheet pullやCookie更新後に再実行できる余地がある。

### failed_actionsへの記録例

トークン切れ:

```json
{"account_id":1,"screen_name":"TamaraRodrigu47","tweet_id":"2063399770534891857","execution_type":"retweet","reason":"TOKEN_EXPIRED_OR_INVALID | HTTP 401 code=32 message=Could not authenticate you","result_snapshot":{"retweet":false}}
```

ロック:


### Sheets同期時の注意

`sheets_sync.py` の `summarize_failure_reason()` は、`error_detail` から短いstatus表示を作る。
開発者がエラー分類を増やす場合は、以下も合わせて更新する。

- `twitter_api.py` の `_classify_api_failure()`
- `test.py` の `CONCLUSIVE_FAILURE_PREFIXES`
- `sheets_sync.py` の `summarize_failure_reason()`
- `tweet_post.py` のSheet反映ロジック
- このドキュメントの分類表

現在の実装では、401/auth/token/ct0系は `トークン切れ` に寄せる。
ロックや凍結をSheet上で明確に分けたい場合は、`summarize_failure_reason()` に `ACCOUNT_LOCKED_OR_CHALLENGE_REQUIRED` と `ACCOUNT_SUSPENDED_DEACTIVATED_OR_OFFBOARDED` の分岐を追加する。
## 機密情報の扱い

エラーログには機密情報が混ざる可能性がある。

外部共有前に必ず伏せるもの:

- Cookie全体
- `auth_token`
- `ct0`
- `cf_clearance`
- proxyのユーザー名/パスワード
- `x-client-transaction-id`
- Google Sheets URLやservice account情報

`Curl Command` は `authorization` と `x-csrf-token` をマスクするが、Cookie文字列やproxy認証情報が残る場合がある。

## 失敗調査の標準手順

1. コンソール末尾の `[ERROR]` / `[WARN]` を見る。
2. `last_error_summary` または `reason` を読む。
3. `failed_actions.jsonl` で対象アカウント・対象ツイート・execution_typeを確認する。
4. `Response Preview` を見る。
5. 401ならSheet/DB/Cookie/Fingerprintを確認する。
6. 200なのに失敗なら成功判定キーワードを確認する。
7. TIDなら `tid_node/server.log` を見る。
8. proxy/通信なら同アカウントで読み取りprobeを実行する。
