# いいね・ブックマーク処理フロー詳細

## 1. 目的

このドキュメントは、指定ツイートに対して「いいね」と「ブックマーク」を実行するときに、どのファイルがどの順番で使われるかを開発者向けに整理したものです。

対象処理:

- `FavoriteTweet` によるいいね
- `CreateBookmark` によるブックマーク
- 実行前の自然フロー
- `x-client-transaction-id` 生成
- Cookie更新保存
- 失敗ログ出力

## 2. 全体のファイル使用フロー

```text
test.py
  ↓
database.py
  ↓
user_agents.py
  ↓
twitter_api.py
  ↓
tid_node/server.js
  ↓
twitter_api.py
  ↓
database.py
```

役割を一言でまとめると以下です。

```text
test.py
  実行入口。メニュー、URL入力、実行件数、並列処理、結果表示を担当。

database.py
  DBからアカウント情報を読み、処理後にCookieを保存する。

user_agents.py
  アカウントごとのUser-Agent、impersonate、sec-ch-uaを決める。

twitter_api.py
  X API操作本体。自然フロー、いいね、ブックマーク、送信処理を担当。

tid_node/server.js
  x-client-transaction-idを生成するローカルNode.jsサーバー。
```

## 3. 実行入口: `test.py`

手動実行では `test.py` を起動します。

```powershell
python test.py
```

いいね・ブックマークの複数アカウント処理は、メニューの選択5です。

```text
5: アカウント並列処理（件数指定可）
```

選択5の入口関数:

```python
test_concurrent_processing()
```

この関数が行うこと:

```text
1. ツイートURLまたはTweet IDを受け取る
2. 実行アカウント数を受け取る
3. DBからactiveアカウントを取得する
4. アカウント一覧をシャッフルする
5. 指定件数だけ抽出する
6. ACCOUNT_PARALLEL_LIMITごとにバッチ化する
7. アカウントごとにbuild_runtime_context()を呼ぶ
8. AsyncSessionを作成する
9. api.natural_action()を呼ぶ
10. 結果を表示する
11. 失敗時はfailed_actionsへ記録する
```

関連定数:

```python
LIKE_ACCOUNT_DB_PATH = "like_accounts.db"
ACCOUNT_PARALLEL_LIMIT = 40
```

選択5では `like_accounts.db` のactiveアカウントを使います。

## 4. DB読み込み: `database.py`

`test.py` は `database.py` の `AccountDB` を使ってアカウントを読みます。

呼び出し:

```python
AccountDB(LIKE_ACCOUNT_DB_PATH).get_active_accounts()
```

取得する主な値:

```text

screen_name
cookies
proxy
status
user_agent
sec_ch_ua
impersonate

```

いいね・ブックマーク処理で特に重要な値:

```text

  UAを決定するために使う。

screen_name
  ログ表示に使う。

cookies
  auth_token、ct0、twidなどを含む。X API認証に使う。

proxy
  リクエスト送信時のproxyとして使う。

status
  activeのアカウントだけ実行対象になる。
```

処理後、Cookie更新がある場合は保存します。

```python
update_cookies(account_id, new_cookies)
```

`test.py` 側では以下を通して呼ばれます。

```python
save_cookies_if_needed(ctx)
```

成功ログ:

```text
[Saved] CookieをDBに保存しました (@screen_name)
```

## 5. 実行環境構築: `build_runtime_context()`

`test.py` の `build_runtime_context()` は、1アカウント分の実行環境をまとめて作ります。

主な処理:

```text
1. DBアカウントからCookieを取得
2. account_idを取得
3. user_agents.pyでUser-Agentを決定
4. User-Agentに合うcurl_cffi impersonateを決定
5. Chrome系ならsec-ch-uaを生成
6. proxyをsocks5h形式へ正規化
7. csrf_tokenとしてCookieのct0を取得
8. TwitterAPIインスタンスを作成
```

返すdictの主な中身:

```text
account
screen_name
cookies
csrf_token
user_agent
browser
sec_ch_ua
proxy
proxies
api
```

`api` が `TwitterAPI` のインスタンスです。

```python
api = TwitterAPI(
    AUTH_TOKEN,
    csrf_token,
    cookies,
    proxy=proxy,
    user_agent=user_agent,
    sec_ch_ua=sec_ch_ua,
)
```

## 6. UA決定: `user_agents.py`

アカウントごとのブラウザらしさを作るファイルです。

使用関数:

```python
get_ua_for_account(account_id)
get_impersonate_for_ua(user_agent)
get_sec_ch_ua(user_agent)
```

決まるもの:

```text
User-Agent
curl_cffi impersonate
sec-ch-ua
```

例:

```text
iOS Safari
  User-Agent: iPhone / iPad Safari系
  impersonate: safari172_ios / safari180_ios
  sec-ch-ua: None

Android Chrome
  User-Agent: Android Chrome系
  impersonate: chrome131_android
  sec-ch-ua: あり

Desktop Chrome
  User-Agent: Windows Chrome系
  impersonate: chrome131 / chrome136など
  sec-ch-ua: あり
```

重要:

```text
Safari/iOS系ではChrome用のsec-ch-uaを送らない。
TID生成時にも同じUA/CH条件を渡す。
```

## 7. X操作本体: `twitter_api.py`

いいね・ブックマークの本体は `twitter_api.py` の `TwitterAPI` クラスにあります。

選択5では、最終的に以下を呼びます。

```python
api.natural_action(
    tweet_id,
    session,
    do_like=True,
    do_bookmark=True,
)
```

`natural_action()` の処理順:

```text
1. Xを開いた最初の画面としてHomeTimelineを必ず取得
2. 応答JSON内に対象ツイートIDが存在するか確認
3. 対象がホームにあれば、一覧上で操作またはTweetDetailへ移動
4. 対象がホームになければ、SearchTimelineまたは直接TweetDetailへ移動
5. 検索結果になければ直接TweetDetailへ移動
6. どの経路でも対象を取得できなければ何も送らず終了
7. 実際に通った経路に対応するclient_eventだけを送信
8. 詳細経路ではメディア閲覧とbottom到達を反映
9. 詳細後のみ一定確率で投稿者プロフィールを閲覧
10. 指定されたlike_tweet() / bookmark_tweet()を実行
11. 2〜4秒待機
```

検索経路では、`TweetDetail`から投稿者名を解決し、`from:投稿者名`を検索語として`SearchTimeline`を最大2ページ取得します。1ページ目で対象ツイートIDを確認できれば即終了し、2ページとも見つからなければ直接TweetDetailへ移動します。Query IDはX配信JavaScriptから解決し、環境変数 `X_QUERY_ID_SEARCH_TIMELINE` でも上書きできます。プロフィールと通知は開始経路に使用しません。

## 8. TID生成: `tid_node/server.js`

いいね・ブックマークでは `x-client-transaction-id` が必要です。

この値は `twitter_api.py` が直接作るのではなく、ローカルNode.jsサーバーへ問い合わせます。

TIDサーバーファイル:

```text
tid_node/server.js
```

ローカルURL:

```text
http://127.0.0.1:3000
```

生存確認:

```text
GET /status
```

TID生成:

```text
GET /tid?path=...&method=POST&ua=...&ch=...&mobile=...&platform=...
```

Python側の確認/起動処理:

```python
_ensure_tid_server_running()
```

TIDサーバーが起動していない場合、Python側が自動起動します。

```text
node tid_node/server.js
```

## 13. 共通送信処理: `_execute_via_native_curl()`

いいねもブックマークも、最後は共通送信処理を通ります。

```python
_execute_via_native_curl(
    url,
    payload,
    referer,
    success_keyword,
    transaction_id,
    session,
)
```

この関数が行うこと:

```text
1. 共通ヘッダーを作る
2. User-Agentを入れる
3. x-client-transaction-idを入れる
4. x-csrf-tokenを入れる
5. Cookieヘッダーを作る
6. proxyを設定する
7. curl_cffiでPOSTする
8. レスポンスをcurl風文字列に変換する
9. success_keywordで成功判定する
10. Set-Cookieがあればself.cookiesへ反映する
11. 失敗時はデバッグ情報を出す
```

現在は関数名に `native_curl` とありますが、実際の送信は `curl_cffi.requests.AsyncSession` で行います。

理由:

```text
TLS指紋とimpersonateを維持するため。
```

## 18. よくある失敗原因

### ProxyError

例:

```text
ProxyError: Failed to perform, curl: (97) connection to proxy closed.
```

意味:

```text
proxy接続が途中で切れた。
TID生成やエンドポイント指定の問題ではない可能性が高い。
```

見分け方:

```text
デバッグログ内にx-client-transaction-idが入っている
しかしcurl_cffi execution exceptionで落ちている
```

この場合はproxy品質、proxy session、region、同時接続数を疑います。

### TID取得失敗

例:

```text
ENGAGEMENT TID取得失敗
Node.js TID server returned no transaction id
```

見る場所:

```text
tid_node/server.log
```

確認すること:

```text
TIDサーバーが起動しているか
古いserver.jsがポート3000を掴んでいないか
UA/CHの組み合わせが正しいか
https://x.com のHTML取得に失敗していないか
```

### Cookie無効

例:

```text
401
code 32
```

見るもの:

```text
auth_token
ct0
twid
cf_clearance
__cf_bm
```

### アカウント制限

例:

```text
code 326
code 226
code 344
```

意味:

```text
追加認証
自動化判定
Cookie劣化
投稿/操作制限
```

## 20. 修正時の注意点

必ず守ること:

```text
疑似TIDフォールバックを復活させない
いいねとブックマークはENGAGEMENT用TIDを使う
TID pathとAPI URLのpathを一致させる
Safari/iOS UAにChrome用sec-ch-uaを付けない
Cookie全文やproxy認証情報を外部共有しない
```

変更後の確認:

```powershell
python -m py_compile test.py
python -m py_compile twitter_api.py

```

動作確認:

```text

選択5: 少数アカウントでいいね・ブクマ実行確認
```

## 21. まとめ

いいね・ブックマークの実行は、単純な2リクエストではなく、以下を組み合わせた処理です。

```text
アカウントDB
Cookie
proxy
User-Agent
curl_cffi impersonate
TIDサーバー
HomeTimeline
TweetDetail
client_event
FavoriteTweet
CreateBookmark
Cookie保存
失敗ログ
```

特に重要なのは以下です。

```text
TIDはtid_node/server.jsで生生成する。
TID取得失敗時は送信しない。
いいね・ブクマ本体はtwitter_api.py。
実行管理はtest.py。
アカウント取得とCookie保存はdatabase.py。
失敗の多くはproxy切断。
```
