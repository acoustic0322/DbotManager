# X非公式API 操作システム 仕様書

## 1. このドキュメントの目的

このドキュメントは、X操作ツール群の構成、処理フロー、TID生成、使用エンドポイント、テストランナー、エラー診断方法を、他の開発者が引き継げる粒度でまとめた仕様書です。

コードを触る前に、まず以下を把握してください。

- 実行入口は主に `test.py`
- X操作の中核は `twitter_api.py`
- `x-client-transaction-id` は `tid_node/server.js` で生成する
- DBアカウントは現在 `like_accounts.db` を使う
- 疑似TIDフォールバックは禁止
- 失敗の多くはTIDではなくプロキシ切断で発生する

このシステムにはCookie、認証情報、プロキシ情報が含まれます。ログやスクリーンショットを外部共有するときは、必ずCookie、auth token、ct0、proxy認証情報をマスクしてください。

## 2. 全体概要

このシステムは、保存済みXアカウント情報を使って、指定ツイートに対する閲覧フロー、インプレッション系イベント、いいね、ブックマーク、投稿、画像アップロードなどを行うためのPythonツール群です。

主な機能:

- ツイート詳細閲覧
- ホームタイムライン取得
- インプレッション系 `jot/client_event` 送信
- いいね
- ブックマーク
- メディア付き/なし投稿
- メディアアップロード
- 複数アカウント並列実行
- Cookie更新のDB保存
- 失敗アクションのログ記録

基本フロー:

```text
DBからactiveアカウント取得
  ↓
Cookie / proxy / UA / sec-ch-ua / impersonate を構築
  ↓
TwitterAPI インスタンス作成
  ↓
TIDサーバー起動確認
  ↓
HomeTimelineでウォームアップ
  ↓
TweetDetail取得
  ↓
jot/client_event送信
  ↓
必要に応じてメディア閲覧待機・プロフィール閲覧
  ↓
FavoriteTweet
  ↓
CreateBookmark
  ↓
Cookie更新をDB保存
  ↓
結果表示・失敗ログ記録
```

### 4.3 `tid_node/server.js`

`x-client-transaction-id` を生成するローカルNodeサーバーです。

使用ライブラリ:

```text
@lami/x-client-transaction-id
linkedom
```

提供エンドポイント:

```text
GET /status
```

生存確認。成功時は `OK`。

```text
GET /tid?path=...&method=POST&ua=...&ch=...&mobile=...&platform=...
```

指定API path/method用のTIDを返す。

内部仕様:

- UA/CHに合わせて `https://x.com` のHTMLを取得
- `ClientTransaction` を初期化
- `generateTransactionId(method, path)` でTID生成
- UA/CH/mobile/platformの組み合わせごとにgeneratorをキャッシュ
- generator最大数は `MAX_GENERATORS = 50`

キャッシュキー:

```text
userAgent | secChUa | secChUaMobile | secChUaPlatform
```

この設計により、iOS Safari、Android Chrome、Desktop Chromeなどのアカウントが混在しても、それぞれのUAに合ったTIDを生成できます。

## 5. TID仕様

### 5.1 TIDとは

XのWeb APIリクエストで必要になる `x-client-transaction-id` ヘッダーです。

この値は単なるランダム文字列ではなく、リクエスト先path、method、Webクライアント側データ、UA/CHの条件に依存します。

本システムでは、以下のAPIでTIDを使います。

- いいね
- ブックマーク
- インプレッション系client_event
- 投稿
- メディアアップロード

### 5.2 疑似TID禁止

過去の実装では、TIDサーバーが失敗した場合にセッション風の疑似TIDへフォールバックしていました。

現在の仕様ではこれは禁止です。

```text
TIDが取れない場合は送信しない
```

理由:

- ブックマークは疑似TIDだと失敗しやすい
- エラー原因がTIDなのかAPIなのか分からなくなる
- 送信ログ上はTIDが入って見えるため、調査が難しくなる

現在の設計:

```text
TID取得成功 → API送信
TID取得失敗 → last_error_summaryに理由を入れてFalse/Noneを返す
```

### 5.3 用途別TID関数

TID生成は用途別に分けています。

```text
TWEET
  _generate_tweet_transaction_id()

ENGAGEMENT
  _generate_engagement_transaction_id()
  FavoriteTweet / CreateBookmark

MEDIA
  _generate_media_transaction_id()
  upload.twitter.com / media upload

CLIENT_EVENT
  _generate_client_event_transaction_id()
  jot/client_event
```

分ける理由:

- ログでどの用途のTID取得に失敗したか分かる
- いいね/ブクマで疑似TIDに落ちないことを保証しやすい
- 投稿系、メディア系、イベント系を個別に調査できる

## 8. UA / impersonate 仕様

`user_agents.py` がアカウントごとのUAを決定します。

基本方針:

- 同じaccount_idなら同じUA
- iOS Safari / Android Chrome / Desktop Chromeを分散
- UAに応じて `curl_cffi` のimpersonateを選択
- Chrome系のみsec-ch-uaを生成

例:

```text
iOS Safari
  impersonate=safari172_ios / safari180_ios
  sec-ch-ua=None

Android Chrome
  impersonate=chrome131_android
  sec-ch-uaあり

Desktop Chrome
  impersonate=chrome131 / chrome136 など
  sec-ch-uaあり
```

TIDサーバーにもUA/CHを渡すため、APIリクエストとTID生成の条件を揃えることが重要です。

## 9. Proxy仕様

proxyはDBアカウントごとに保持します。

正規化:

```text
SOCKS5://... → socks5h://...
```

理由:

- `curl_cffi` でDNS解決をproxy側に寄せるため

よくある失敗:

```text
ProxyError: curl: (97) connection to proxy closed
```

これはTIDエラーではなく、proxy接続が途中で切れた状態です。

ログに生TIDが入っているのに失敗している場合、まずproxyを疑ってください。

## 12. 選択5の詳細仕様

選択5:

```text
アカウント並列処理（件数指定可）
```

入力:

```text
ツイートURLまたはID
実行アカウント数
```

処理:

```text
activeアカウント全件取得
  ↓
random.shuffle(accounts)
  ↓
指定件数だけ抽出
  ↓
ACCOUNT_PARALLEL_LIMITごとにバッチ化
  ↓
asyncio.gatherで並列実行
```

結果表示:

```text
結果:
1. @account: [OK] (35.86s)
   インプレッション=True いいね=True ブックマーク=True

成功: 13/15
```

成功条件:

```text

```

補足:

- インプレッションだけ成功しても選択5の総合成功にはならない
- いいね/ブクマのどちらかがFalseなら `[NG]`
- `ProxyError` はTIDではなく通信経路の問題として扱う

## 13. 選択11の詳細仕様

選択11:

```text
インプレッション事前確認（送信なし）
```

目的:

- client_event用TIDが生成できるか確認する
- 実際のclient_eventは送らない
- TIDサーバーやUA/CHの問題を切り分ける

## 14. TIDサーバー運用

### 14.1 起動確認

```text
http://127.0.0.1:3000/status
```

期待値:

```text
OK
```

### 14.2 古いTIDサーバー問題

過去に、別フォルダや古い `server.js` がポート3000を掴んでいたことでTID生成が失敗したことがあります。

症状:

```text
HTTP Error 500: Internal Server Error
TID Server returned no transaction id
```

確認方法:

```powershell
Get-CimInstance Win32_Process -Filter "name = 'node.exe'" | Select-Object ProcessId,CommandLine
```

見るポイント:

- `tid_node/server.js` の絶対パスで起動しているか
- `node.exe server.js` のような相対起動になっていないか
- 別プロジェクトのNodeがポート3000を掴んでいないか

古いプロセスがいた場合:

```powershell
Stop-Process -Id <ProcessId> -Force
```

次回の `TwitterAPI` 初期化時に最新版のTIDサーバーが起動します。

### 14.3 TIDサーバーログ

```text
tid_node/server.log
```

正常例:

```text
Fetching X migration data...
TID Generator initialized successfully.
```

例外が出ている場合は `TID Generation Error:` を確認してください。

## 15. よくあるエラーと見方

### 15.1 ProxyError


- proxy接続が途中で切れた
- X APIやTIDの問題ではない可能性が高い

確認:

- 同じアカウントのproxy region/session
- IP確認メニュー
- 同一proxyで複数リクエストが落ちていないか

### 15.2 TID取得失敗

例:

```text
ENGAGEMENT TID取得失敗
CLIENT_EVENT TID取得失敗

```

- TIDサーバーが起動しているか
- 古いNodeがポート3000を掴んでいないか
- `tid_node/server.log`
- UA/CHの組み合わせ
- `https://x.com` のHTML取得が失敗していないか

### 15.3 Cookie無効


- `auth_token`

## 16. 開発時の注意

### 16.1 TIDまわりを変更するとき

必ず守ること:

```text
疑似TIDフォールバックを復活させない
用途別TID関数を維持する
TID pathは実際のAPI pathと一致させる
UA/CHをTIDサーバーへ渡す
Safari系にChrome CHを送らない
```

変更後の確認:

```powershell
python -m py_compile twitter_api.py
node --check tid_node/server.js
```

動作確認:

```text
選択11でTID preflight
選択5で少数アカウントテスト
```

### 16.2 エンドポイントを変更するとき

確認するもの:

- URL
- TID path
- queryId
- variables
- features
- fieldToggles
- success keyword
- referer

特に、URLとTID pathがズレると失敗しやすいです。

例:

```text
URL:
https://x.com/i/api/graphql/aoDbu3RHznuiSkQ9aNM67Q/CreateBookmark

TID path:
/i/api/graphql/aoDbu3RHznuiSkQ9aNM67Q/CreateBookmark
```

### 16.3 ログを共有するとき

必ずマスクするもの:

```text
authorization
x-csrf-token
auth_token
ct0
twid
proxy user/pass
Cookie全文
```

`_execute_via_native_curl()` のデバッグログは一部マスクしますが、Cookieやproxy情報が残ることがあります。外部共有前に必ず確認してください。
