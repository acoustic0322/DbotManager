# 今回の変更内容まとめ

作成日: 2026-06-20

## 1. 変更の目的

いいね・ブックマーク前の取得経路、Referer、client_eventを一致させ、実際に取得できた対象ツイートにだけ操作する構成へ変更した。

最終的なフローは次のとおり。

```text
Xを開く
→ HomeTimelineを必ず取得
→ 応答JSON内に対象ツイートIDがあるか確認
→ ホームにあれば一覧上で操作、またはTweetDetailへ移動
→ ホームになければSearchTimeline、またはTweetDetailへ直接移動
→ SearchTimelineは最大2ページ取得
→ 検索でも見つからなければTweetDetailへ移動
→ 実際の画面に対応するclient_eventを送信
→ いいね・ブックマーク
```

## 2. 変更したファイル

### 2.1 `twitter_api.py`

主な実装変更はこのファイルに集約している。

#### importとGraphQL操作キャッシュ

対象箇所: 15行目、23行目付近

- `re` を追加した。
- `_graphql_operation_cache` を追加した。
- X配信JavaScriptから解決したQuery IDを再利用する。
- ブラウザ・アカウンごとの差異に対応するため、SearchTimelineのQuery IDは固定していない。

#### `view_tweet()` / TweetDetail解析

対象箇所: 334行目付近

- TweetDetailから対象ツイートの投稿者名とメディア情報を取得する。
- Xの新しい応答構造に対応した。

```text
旧: user_result.legacy.screen_name
新: user_result.core.screen_name
```

- 新旧両方を確認するフォールバック構成にした。
- 画像、動画、テキストの判定は従来の`extended_entities.media`を使用する。

#### `_timeline_features()`

対象箇所: 1019行目付近

- ChromeのNetworkで取得したSearchTimelineの実測`features`へ合わせた。
- SearchTimelineに不要な`fieldToggles`は送信しない。

#### `_json_contains_tweet_id()`

対象箇所: 1064行目付近

- GraphQL応答を再帰的に調べる。
- `rest_id`、`id_str`、`tweet_id`のいずれかが対象IDと一致するか確認する。
- APIがHTTP 200を返しただけでは「対象取得成功」と判定しない。

#### `_find_bottom_cursor()`

対象箇所: 1078行目付近

- SearchTimeline応答から`cursorType = Bottom`の`value`を探す。
- 2ページ目を取得する際の`cursor`に使用する。

#### `_resolve_graphql_operation()`

対象箇所: 1094行目付近

- Xの検索ページHTMLと配信JavaScriptを取得する。
- JavaScript内の`operationName = SearchTimeline`に対応する`queryId`を解決する。
- HTML/JavaScript取得にAPI用Authorizationヘッダーを付けると401になるため、ブラウザ用ヘッダーへ分離した。
- 環境変数`X_QUERY_ID_SEARCH_TIMELINE`による上書きも可能。

#### `_fetch_timeline_operation()`

対象箇所: 1177行目付近

- GraphQL GETごとに正規の`x-client-transaction-id`を生成する。
- `User-Agent`、`Referer`、TIDを付けてSearchTimelineを取得する。
- `max_pages`を追加した。
- 1ページ目で対象IDを確認できた場合は即終了する。
- 見つからない場合だけBottom cursorで次ページを取得する。

#### `fetch_search_timeline()`

対象箇所: 1246行目付近

- TweetDetailから投稿者の`screen_name`を取得する。
- 検索語は`from:screen_name`形式。
- SearchTimelineを最大2ページ取得する。
- 検索応答に対象ツイートIDが実在する場合だけ`True`を返す。
- 実際の検索語を`last_search_query`に保存し、Refererと一致させる。

#### `fetch_home_timeline()`

対象箇所: 1274行目付近

- 引数`tweet_id` を追加した。
- `tweet_id` 指定時は、HomeTimeline応答内に対象IDが存在するか確認する。
- 対象がないのにホーム経由のclient_eventを送らない。
- `tweet_id` 未指定時は、従来どおりウォームアップ成功の真偽値を返す。

#### `send_client_event_log()`

対象箇所: 1306行目付近

引数に次を追加した。

```text
page
include_stream_results
include_bottom
```

- ホーム一覧: `home/stream/results`
- 検索一覧: `search/stream/results`
- 詳細画面: `tweet/stream/results`
- 詳細の下部到達時のみ: `tweet/bottom`
- 経路で発生していないイベントはpayloadへ含めない。
- X側エンドポイントの再試行と成功判定は維持した。

#### `natural_action()`

対象箇所: 1460行目付近

- 処理開始時にHomeTimelineを必ず取得する。
- HomeTimeline内に対象IDがある場合は、ホーム一覧上で操作するかTweetDetailへ移動する。
- HomeTimeline内にない場合は、SearchTimelineまたは直接TweetDetailへ移動する。
- SearchTimelineで見つからない場合はTweetDetailへ移動する。
- いずれの経路でも対象を取得できない場合は、client_event・いいね・ブックマークを送らず終了する。
- 詳細経路ではメディア種別に応じた待機を行う。

```text
動画: 15〜30秒
画像: 8〜15秒
テキスト: 4〜12秒
```

- 詳細後の投稿者プロフィール閲覧分岐は維持した。
- プロフィールと通知は開始経路から削除した。

## 5. 現在の制約と注意点

- HomeTimelineはパーソナライズされるため、任意の対象ツイートが必ず入るわけではない。
- SearchTimelineは最大2ページ、各1ページ20件を基本とする。
- 古い投稿は2ページでも見つからない場合がある。
- 検索で見つからない場合はTweetDetailへ移動する。
- client_event送信成功と公開インプレッション数の増加は1対1で対応するとは限らない。
- Query IDとXのGraphQL応答構造は今後も変更される可能性がある。
